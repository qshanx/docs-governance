# 执行复盘

让下一次执行更可靠、更省力。关注工作条件和执行方式的改进；本次文档对齐与文档体系审计仍由各自流程负责。

## 什么时候触发

- 用户明确要求复盘一次会话、任务、故障或阶段。
- 项目已约定在里程碑或阶段结束时复盘。
- 同类问题反复出现或收到重要纠正时，可以建议复盘，不默认每轮都执行。

未指定范围时只看当前会话。指定历史范围时按需读取对应日志、diff、检查结果和用户确认；材料不可访问就说明缺口，不从印象补全过程。

## 复盘什么，结果放哪里

| 观察到的现象 | 核对与改进方向 | 获准落实后的去向 |
|---|---|---|
| 找资料绕路、反复探索、遗漏隐含关联 | 是否缺少有效指针或位置提示 | 现有 MAP／文档索引 |
| 错误本可自动发现 | 先读已有检查命令、测试、Hook、CI，判断是缺检查、未接入还是失效；按成本建议最小修复 | 现有测试或检查配置；需要排期则进已有任务系统 |
| 规则含糊、冲突或审查漏项 | 机械可判定的问题优先考虑自动检查；需要判断的约束澄清适用条件与案例 | 对应主规则或现有评审规范 |
| 入口太长、重复或指令没有实际作用 | 对照本次行为判断哪些该精简、下沉或删去，不能只凭行数决定 | 按 `skills/agent-entrypoints/SKILL.md` 处理项目入口；细节归现有文档 |
| 重复读取、输出过大、工具调用成本高 | 能否定向读取、合并查询或缩小输出；成本无测量就不报节省比例 | 对应操作指南或工具配置 |
| 缺少关键日志、状态或外部信息 | 指出缺什么、影响哪个判断，优先建议已有的只读信息入口 | 对应运行指南或待办；权限变更另按授权处理 |

不强制新建规范文件、评审 Agent 或 Hook；没有自动门禁是否构成问题，要结合项目风险和本次证据判断。

## 怎么复盘

1. **找证据**：从约定范围提取真实错误、返工、用户纠正和有效做法，记录位置与结果，区分事实和原因假设。
2. **筛选建议**：沿上表检查，优先复用或修复已有机制。只保留未来能改变行动的发现，写清适用条件，合并重复建议；已经解决的说明现有措施，不再造一套。
3. **给出落点**：默认在回复中按影响排序，逐项写“问题与证据 → 下次如何处理 → 对应主记录或检查”。没有可复用发现就说明，不凑结论。

复盘请求本身不授权改文件、安装检查或创建外部任务。用户要求落实时，在已有授权内更新上表对应位置；跨项目或全局配置不随项目复盘自动扩大范围。

复杂复盘确需保存时，沿用项目已有复盘位置；LOG 只追加重要改进及详细记录的索引。无需另建 MEMORY.md 或 Skill，经验也不自动升级为常驻规则。

## 完成标准

- 明确实际查看的范围与缺失材料，不把当前会话结论推广成整个项目结论。
- 每条建议有证据、适用条件、具体动作和落点，区分已确认经验、待验证假设、待执行建议。
- 建议与已落实、已验证结果分开；没有执行的改进不称已修复或已生效。
