# Agent 入口八项规范

### 1. 每份入口不超过 200 行

先检查读完能否回答：做什么产品、用什么技术、新代码放哪里；尚未确定的内容如实标明。

每份 AGENTS.md／CLAUDE.md（含模块入口）≤200 行；超长细节下沉，保留关键规则和读取路标。生成、修改或审查后，运行[计数脚本](../../../scripts/check-entrypoint-length.py)检查本次全部受检入口，非零退出即不通过：

```sh
python3 <插件目录>/scripts/check-entrypoint-length.py <入口文件> [更多入口文件...]
```

### 2. 写清禁止引入什么，以及替代方案

先查已确认的技术选型、历史兼容问题和禁改区，判断哪些依赖或方案会破坏项目约束。对有依据的禁用项写清“对象与范围 → 原因 → 替代方案／决策入口”；需要评审的单列，没有已确认禁用项则如实报告。

### 3. 让规则可以执行和判定

写清该怎么做、怎样判断遵守；涉及命令时，再补工作目录、必要环境和通过条件。命令取自目标项目，优先核对构建、测试、启动及不明显的环境前置条件；长说明留在已有操作或测试文档。代码风格与命名只补项目特有约定，工具已有规则直接引用。

以[设备借用台账](examples/confirmed-project.md)这个虚构项目为例，命令仅适用于该案例：

| 写法 | 规则 |
|---|---|
| 含糊 | 修改后注意测试，保证代码质量。 |
| 可执行 | 修改实现后，在项目根目录激活已有 `.venv`，运行 `python -m pytest -q`；退出码为 0 才算本次测试通过，非零则先定位失败原因。 |

交付时的区别（仅示例，不是实际运行结果）：

- 只从开发说明找到命令，尚未执行 → 已定位，未验证。
- 实际执行，退出码 0 → 本次测试通过。
- 实际执行，退出码非零 → 本次检查失败，附失败输出摘要。

### 4. 渐进式披露：入口留指针，知识按需展开

目标项目已启用 `writing-for-agents` 且允许维护入口时，给面向 AI 的文档写作留读取指针；不复制规则或生成未启用的调用。

详细知识保留在各自文档，入口只留必要规则和读取指针。Agent 先读入口，任务需要某项知识时再沿指针读取相关内容；资料多时先到索引，再到具体文档或章节。

例如：

```text
修改模块边界前 → 读取 ARCHITECTURE.md 中相关模块的职责与依赖。
```

资料多或位置不明确时，先读 `CLAUDE_MAP.md` 等索引，再到正文。示例路径替换为项目真实位置，选一两个典型任务沿指针找到所需内容；涉及实现时对照代码或配置，指出过时说明与冲突。自动导入全部正文仍会占用上下文。

接入本插件模块变更流程时，在获准的共享入口保留触发条件及 `skills/documentation/docs-governance/SKILL.md` 的“模块变更流程”指针，使用实际安装路径，外部插件使用完整路径。

### 5. 敏感模块有专属约束时，再加局部入口

本 Skill 从项目层面判断是否需要局部入口。默认使用根入口；模块有已确认的业务职责、状态归属、公共接口或专属操作约束时，再按目标宿主支持的方式增设。不按每个目录批量生成空壳，也不把一个目录直接认定为 DDD 限界上下文。

采用模块两入口布局时，按需维护：

- `AGENTS.md`：适用范围、负责／不负责的业务、状态写入者、公共接口入口、允许／禁止依赖、验证命令和简短决策；只保留相对父级新增的规则。
- `CONTEXT.md`：本上下文术语、关系和歧义，执行 `domain-modeling`；无独立领域语言时引用已有词汇表，不强制创建。

AGENTS 是模块开发约束与导航，不是模块百科：不收纳完整需求、字段清单、实现教程、实时任务或测试流水；这些内容链接既有主记录。CONTEXT 不收纳开发指令、接口实现或决策理由，不能成为另一份 AGENTS。两者使用同一模块／上下文标识；AGENTS 明确指向实际词汇表，CONTEXT 标明适用范围和对应模块入口，只互相导航、不复制正文。

模块入口可有一条开发路标，替换为真实路径后使用：“修改本模块前，先读适用的父级规则和本入口，再读指定的 CONTEXT 及本次相关契约／决策；跨模块读取双方。”这是读取规则，不代表每次修改都调用 module-governance；模块建档／约定维护按用户任务意图识别，无须点名。外部 Skill 指向实际安装位置，不把不存在的插件相对路径写进项目。此约定不替代宿主加载验证。

接口协作信息可放在 AGENTS 的“接口契约”节，字段和类型仍链接唯一代码／机器定义，执行 `contract-first` 的入口复用规则。简短模块决策按 `domain-modeling` 的内联规则记录；已有契约文件和 ADR 只挂引用，不搬迁或复制。“两入口”不是禁止保留历史与详细规格，超出 200 行时下沉细节到既有主记录。

根入口应明确：修改模块前，定位并读取该路径适用的父级与模块入口，以及被引用的相关契约／术语；跨模块变更读取双方。不承诺宿主从仓库根自动加载全部子目录入口；链接存在也不证明 Agent 已读。规则冲突先查适用范围与宿主规则，不能无条件认定子级覆盖父级安全约束。文档与代码核对委托 `architecture-docs`，不是以入口存在代替边界检查。

例如，假设认证模块已确认以下额外规则和测试命令，可在模块入口写：

```markdown
# src/auth/AGENTS.md
- 适用于 src/auth/ 及其子目录。
- 修改 token 验证逻辑须有明确要求，变更须经过项目既有 review 流程。
- 新增认证方式时，同步补充对应测试。
- 认证代码变更后，在项目根目录运行 `pnpm test src/auth`，退出码为 0 才算测试通过。
```

文件名沿用已确认布局，并核对宿主兼容要求；只写相对根入口增加的规则。检查父子规则冲突、受限与无关模块的生效范围，并按第 1 条计数；无专属约束时标不适用，未实测宿主加载时标未验证。

### 6. 可用 Hook／CI 承接规则的执行

入口留规则和 Hook／CI 配置位置，触发时机查配置，执行效果看运行证据。能在违规时阻断目标动作的 Hook，可作为规则的强制执行层。对容易漏做、又能由程序判断的检查，按项目需要选择，优先复用已有工具。

以下是可选思路，工具和触发事件按目标项目、宿主核对：

| 场景 | 执行方式示例 |
|---|---|
| 编辑后自动格式化 | Claude Code 的 `PostToolUse` → 项目已有格式化工具，如 Prettier |
| 核心模块变更后自动测试 | `PostToolUse` → 项目已有的相关测试命令，反馈失败结果 |
| 敏感目录修改前需要确认 | `PreToolUse` → 按项目约定请求确认或拒绝本次操作 |
| 入口超过 200 行时阻止提交 | Git 提交前 Hook → 第 1 条计数脚本，失败时拦截提交 |

自动运行、失败提醒与阻断操作分别说明；事后 Hook 不能阻止已经发生的操作，CI 要阻止合并还需设为必需检查。实际接入须在授权内保留既有配置，用安全的成功／失败样本验证效果；交付标明已验证、仅有配置、仅建议或不适用。

### 7. 用已有文档形成长期记忆

在入口简要约定：

- **记什么**：能影响后续工作的明确纠正、已验证做法和已知陷阱，保留必要的适用条件与依据。
- **放哪里**：稳定规则写共享入口，领域术语写对应上下文，关键决策沿用既有主记录；测试入口、使用方法或重要覆盖事实变化才改 TESTS。重要历史沿用已有记录，不把一次纠正或普通测试结果同时写入 LOG、MAP 和 TESTS。
- **何时更新**：有确认的新经验就更新对应文档；条件变化时复核，有依据再修订，有效红线保留。

例如，确认集成测试需要先启动测试用 Redis：只补进 `TESTS.md` 的前置条件；无需为同一事实再写 LOG、MAP。普通小修不产生文档事实变化时，只改代码、跑相关检查。

需要约定上下文压缩时，可补一句：“压缩摘要保留当前目标、关键约束、验证结果、未决项和资料位置。”这是摘要的保留要求，实时任务内容仍留在会话或任务记录中。

检查一条经验能否按任务找到、是否仍适用；依据不明标待核实，尚无经验如实报告，只读审查仅给建议。

### 8. 写入已确认的协作方式

- **写什么**：已确认的沟通语言、回复详略、关注重点、交付方式，以及哪些事自主推进、哪些需确认。只选实际影响协作的内容。
- **放哪里**：项目共识写已选定的共享入口；跨项目个人偏好写 `~/.claude/CLAUDE.md` 或 `~/.codex/AGENTS.md`，按宿主选用；单次要求留当前任务。

例如，项目已确认以下习惯时，可写：

```markdown
## 协作方式
- 默认中文，先给结论；交付时简述改动和验证结果。
- 已明确范围内的小调整直接推进；新增业务取舍先确认。
```

按实际约定取舍，沿用已有提交／推送授权；仅记录协作所需的稳定偏好。
