# 文档结构

借鉴“深模块、浅接口”：同一职责的完整资料聚在目录内部，对外提供简洁的读取入口。深指内容内聚，不是目录层级深；按资料用途分类，不按 Markdown 等文件格式分类。

## 流程

1. **了解现状。** 阅读现有入口、文档和相关对话，确认常见任务、资料用途与已有主源，明确本次是规划、整理还是只读审查。

2. **按职责归类。** 将同类、服务同一职责的资料放在一起，判断一起读取或修改是否更方便。优先复用已有目录；资料分散或职责混杂时再新建、合并或拆分，给出归属理由，不套固定目录模板。

3. **安排浅入口。** 详细内容留在职责目录，明确每项信息的主记录，其他位置引用。资料多时提供简短索引，说明何时读哪份；资料少时直接链接正文。将实际路径交给 `agent-entrypoints` 接入项目入口与 MAP，避免重复正文、目录树镜像和层层空转。

4. **验证并交付。** 用一两个真实任务从入口找到所需正文，检查归属、重复主源、断链和多余跳转。规划交付路径、职责与取舍；整理在授权内落实并更新受影响引用，核对原有有效内容未丢失；只读审查仅报告问题与建议。说明验证结果和剩余缺口。

## 例子

数据库资料分散时，可以集中到已有数据库目录或新建 `docs/database/`，内部放数据模型、表结构、读写边界和迁移约定；入口只需说明“修改数据结构前，读取数据库目录中的相关说明”。设计资料同理，可按职责聚在 `docs/design/`。目录名按项目选择，一份文档已能说清时无需拆出多个文件。
