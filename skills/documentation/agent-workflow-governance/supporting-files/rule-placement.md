# 治理规则与工作流落点检查

整体体检项目治理体系，或用户要求精简入口约束、将散落资料沉淀成 Skill、评估脚本／Hook 时读取。输入为目标根、任务范围、已确认项目规则、资料入口、现有 Skills 和检查配置；缺失项标未验证。默认只读诊断，不安装 Hook、不修改门禁、不移动或删除原文。

## 1. 按任务盘点规则

从 AGENTS.md／CLAUDE.md 及地图进入，沿代表性任务读取涉及的现行规范、操作说明、Skill 附件、脚本、测试和 Hook／CI 配置。给规则记录来源、作用域、触发条件、责任方与现行主源；不把历史解释或一次授权升级为永久规则。

先列覆盖目录和任务，再逐项标有问题、未发现问题、不适用或未验证。大型项目按模块分批，未检查正文不能仅凭索引称已覆盖。静态证据可复用项目健康采集流程；全局配置、个人记忆和历史会话不在本检查范围。

## 2. 判断承载位置

| 规则需要什么 | 优先落点 | 判断要点 |
|---|---|---|
| 开始任务就必须知道的稳定边界与可靠命令 | 项目共享入口 | 只留少量约束和读取指针；局部规则不提升为全局规则 |
| 理解上下文、权衡、组织多步任务 | 现有 Skill | 说明何时用、输入、步骤、输出、停止条件；先查已有职责，不因一段长文就新增 Skill |
| 只在某类任务用到的知识、案例或步骤分支 | 所属 Skill 的 supporting files | 主文件保留触发导航与核心约束；无需每次读取的细节才下沉 |
| 项目当前事实、需求、接口、架构决定与原始证据 | 原项目主记录 | Skill 引用而不复制；减少常驻读取不等于删除事实或撤销约束 |
| 能由明确输入稳定判定的事实 | 现有脚本／测试 | 优先复用；输出范围、位置、退出码与缺口；语义正确性不能靠关键词冒充 |
| 已有可靠检查必须在确定事件触发 | Hook／CI 调用现有脚本 | 先确认触发时点、输入快照、耗时、误报和失败处理；不是每条脚本都需要 Hook |
| 产品取舍、权限扩大或不可逆操作 | 当前授权与必要人工决定 | 检测与执行分开，不把建议、配置或文档当成授权 |

## 3. 核对散落资料能否沉淀

找散落在 README、操作说明、审计报告等处的重复任务方法，判断是否具有稳定触发、可获得输入、可复用步骤、明确产物和停止条件。区分：

- 已有 Skill 覆盖：建议修正调用指针或把缺失步骤补回原主源，不再造一个同职责 Skill。
- 只是特定分支／长案例：建议成为已有 Skill 附件，并写明何时读取。
- 稳定独立工作流且没有所属 Skill：列为新 Skill 候选，附复用证据及与现有职责的边界；本检查不自动创建。
- 单项目事实、历史原文、临时排障或尚无复用证据：留原记录；可提出待验证候选，不直接泛化。

每项迁移建议列出原章节、拟保留内容、拟转移内容、原处指针及约束保留检查。历史证据保留，当前规则只有在确认新主源与等价覆盖后才能退役；只读阶段不删除。目标是减少重复约束与无关加载，不按文件数或行数承诺收益。

## 4. 核对自动化是否值得接入

对可脚本化项检查输入是否可得、判定是否稳定、有无成功／失败／不相关变化样例、执行成本和恢复方式。先查现有脚本、测试、Hook 和 CI 的调用链，区分“已实现”“已配置”“在当前宿主验证生效”。已有措施只缺调用时建议接通，不重复实现。

Hook 建议须列出事件、受检快照、预期耗时或测量缺口、误报风险、失败提示与修复路径；行为尚未验证时先建议手动或提示模式。复杂业务判断留在 Skill／人工审查。涉及写入的工作流检查授权边界与宿主调用控制；配置字段依目标宿主官方说明核对，不将一个宿主的开关作为跨端通用保障。

## 5. 交付与停止

交付表：规则／工作流 → 证据路径与行号／章节、版本 → 当前载体 → 建议落点及复用对象 → 保留或迁移理由 → 最小下一步 → 验证方法。分开已覆盖项、确定缺口、待核实和非本轮范围，按影响而不是数量排序。

只读任务交付即停止，不因发现自动化机会就安装或触发有副作用的工具。证据、主源或授权不明时只暂停依赖它的结论，继续独立项；没有合适的沉淀项也可完成检查，不强造 Skill。缺少宿主行为证据时不能宣布治理体系全部有效。

从历史对话、跨次测试或故障中挖掘经验属于后续审计，按明确提供的来源与授权范围开展，优先复用 docs-retro；本流程不隐式扫描会话历史。
