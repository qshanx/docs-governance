# 项目经验复盘

把历史中的有效经验变成下一次能找到、能采用、能验证的项目知识。本次文档对齐由日常维护负责；文档体系是否准确、完整由审计负责。

## 什么时候触发

- 用户要求复盘一次会话、任务、故障或阶段。
- 项目已约定在里程碑或阶段结束时复盘。
- 同类问题反复出现或用户重复纠正时，建议针对该问题复盘，不默认每轮执行。

未指定范围时只看当前任务及其会话。追溯历史时，从问题、模块或关键词检索相关对话和 PROJECT_LOG，再沿链接读取 Issue、PR、决策及测试证据，不全文加载所有日志。材料不可访问就说明缺口，不从印象补全过程。

## 从六个方向找经验

| 方向 | 去哪里找、重点核对什么 | 值得留下什么 |
|---|---|---|
| 用户纠正 | 对话中的纠正及后续确认：是一次要求，还是反复适用的约定？ | 已确认的稳定约定及适用范围 |
| 重复踩坑 | LOG 的故障、返工记录及关联 Issue：同类问题为什么再次发生？ | 原因、预防办法和验证入口 |
| 难找的知识 | 对话中的反复搜索、定位过程：哪些关系无法从目录看出来？ | 导航指针、隐含依赖和定位提示 |
| 决策理由 | 讨论、PR、ADR：为什么选这个方案，哪些条件限制了选择？ | 已确认的理由、取舍及重新评估条件 |
| 有效做法 | 成功处理问题的过程和测试证据：什么办法在什么条件下有效？ | 可复用步骤、必要条件和验证方法 |
| 过期或冲突经验 | 历史结论对照当前实现、需求和主记录：哪些已失效或互相矛盾？ | 修订或替代依据，保留历史上下文 |

六个方向是查找提示，不要求每次凑齐六条结论。普通进度、一次性操作和未经验证的猜测不升级为长期规则。

## 怎么处理，放在哪里

1. **核对证据**：记录来源位置与结果，区分事实和原因假设；对照当前实现、已确认需求及已有经验，判断是否仍适用。实现与需求冲突分别记录，不能用代码现状反向批准需求。
2. **筛选并合并**：只保留未来能改变行动的经验，合并重复；已经解决的说明现有措施。一次失败不直接变成永久禁令，证据不足先列待验证建议。
3. **给出落点**：默认在回复中按影响排序，每条写“适用情况 → 下次怎么做 → 证据来源”，并指出项目中的具体主记录及下次读取时机。没有可复用发现就不新增内容。

沿用项目实际路径与同类主记录，不为凑齐下列文件另建一套：

- 稳定约定 → `AGENTS.md／CLAUDE.md`；按 `skills/documentation/agent-entrypoints/SKILL.md` 处理，长说明留指针。
- 导航知识 → MAP；领域知识 → `CONTEXT.md`。
- 重要决策 → ADR；可复用操作 → 对应操作文档。
- 可自动防止的重复错误 → 现有测试或检查；先核对已有机制是缺失、未接入还是失效，不重复造检查。
- `PROJECT_LOG` → 只追加重要改进事件及落点链接，不复制经验正文，不改写旧事件。

例如：改接口字段时，从相关指南提取并运行调用示例，避免只改契约却遗漏接入说明；附实际失败与复验依据，写入现有接口验证指南，并从相关任务入口指向它。

复盘请求本身不授权改文件、安装检查或创建外部任务；用户要求落实后，在已有授权范围内更新对应位置。复杂复盘需要保存时沿用已有复盘目录，不默认新建 MEMORY.md、Skill 或全局规则。

## 完成标准

- 明确实际查看的范围与缺失材料，不把当前任务结论推广成整个项目结论。
- 每条经验有依据、适用条件、具体动作和落点，能说明下次如何找到；区分已确认经验与待验证假设。
- 建议、已落实和已验证分开；没有执行的改进不称已修复，写进文档不等于已经有效。
