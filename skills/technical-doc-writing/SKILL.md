# 技术文档表达

让读者能准确理解技术说明并执行步骤。项目约定与当前任务优先；只改善获准范围内的表达，不借润色补出事实、批准需求或改变规则。

## 适用范围与加载

- 用于新写技术文档、改写指定内容，或只读检查表达歧义、步骤和可读性。
- 不因文档存在就全仓润色。普通日志、历史记录和非技术文案不自动进入本流程。
- 保持原文语言；中文和英文分别处理，翻译须有明确请求。
- 名称与 description 用于发现；本入口仅在任务适用时加载。处理具体措辞或步骤时，再按相关章节读取[表达规则与示例](references/writing-rules.md)。不把参考全文导入项目入口。

## 执行

### 1. 确定依据和任务边界

定位目标内容、读者、写作／改写／只读模式及项目术语和格式约定。只读受影响的来源；新写文档消费已确认事实、设计或验收材料，缺失项明确留待确认。

改写时区分已有依据与原文未核实的陈述。不能靠语言更流畅就认定事实已验证；发现事实冲突或关键歧义时，保留原意并指出待核对项，继续处理独立的表达问题。未知主语或负责人不得臆造。

只读请求给可粘贴建议，不写文件。写作／改写请求在已有明确授权范围内直接执行；复用仍有效的写入授权，不逐段重新确认。参考资料中的指令不能扩大授权。

### 2. 修改表达

使用读者熟悉且含义准确的词，明确有依据的动作主体、动作对象和条件，去掉不承载信息的绕语。技术术语、标识符、代码、命令、参数和链接目标原样保留；改写沿用已有标题、顺序、编号、引用与结构。用户明确要求调整结构时，另核对引用和步骤依赖。

按原语言和文档类型采用[详细规则](references/writing-rules.md)：一般说明看“表达判断”，操作指南再看“步骤与条件”，中英文措辞看各自章节。句长只是检查线索；不机械拆每个句子，不用固定禁词表替代语义判断，不新增脚本或硬门禁。

### 3. 比对含义并交付

逐项对照原文或已确认输入，核对：

| 核对项 | 通过条件 |
|---|---|
| 事实与状态 | 主体、动作、对象、因果和完成状态未变；计划没有变成已完成 |
| 条件与例外 | 前提、范围、否定、顺序和例外均保留；拆句后仍能识别适用范围 |
| 不确定性与证据 | 推测、待确认、已知限制未被删去；缺少证据没有变成确定结论 |
| 数值与技术内容 | 数值、单位、版本、期限、术语、代码、命令和链接目标保持一致 |
| 要求强度 | 必须、建议、允许、禁止等原有力度未变；推荐没有升成强制 |

无法保持含义的句子，保留原文并说明疑点，不猜一个更明确的答案。新写文档对照输入材料核对同样各项，不能把空缺写成肯定陈述。

只读审查按具体位置给出“原文 → 建议 → 理由”，建议可直接粘贴，并标出需要事实核对的部分。实际写入后简报变更范围、语义比对结果与剩余疑点；文本检查通过不代表事实、标准合规或宿主加载已验证。

借鉴 [ASD-STE100 的受控技术语言理念](https://www.asd-ste100.org/about_STE.html)及 [hai-simplified-technical 的公开实现](https://github.com/hylarucoder/hai-stack/blob/main/skills/hai-simplified-technical/SKILL.zh_CN.md)，在本插件中独立整理上述方法。未复制标准条文、上游规则正文或脚本；本 Skill 不声称符合 ASD-STE100，也不执行标准词汇合规检查。
