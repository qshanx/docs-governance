## 1. 背景

`docs-governance` 当前主要治理两类事实：

1. 活文档是否仍然反映真实代码和项目状态；
2. 模块发生改动后，应该运行哪些已有测试，防止“改 A 坏 B”。

第二类能力已经由模块回归体系承担：

- 方法论：`skills/engineering/module-regression/SKILL.md`
- 审查 Agent：`agents/regression-auditor.md`
- 命令入口：`commands/regression-audit.md`
- 台账模板：`templates/REGRESSION.example.md`

但目前还缺少一层更靠前的测试协作治理：

> 一个项目究竟有哪些重要规则需要测试？哪些规则已经覆盖？哪些仍是测试缺口？新增需求或修复 Bug 时，应该补什么测试？

现有 `REGRESSION.md` 能回答“改完以后跑什么”，不能完整回答“本来应该测什么”和“为什么要测”。因此拟新增一份测试清单与测试协作方法论；专职测试审查 Agent 属二期选项，v1 不实现。

## 2. 目标

新增测试协作能力后，希望形成下面的闭环：

```text
入口 A：扫描项目已有测试          入口 B：需求 / 业务规则 / Bug 清单
        ↓                                  ↓
形成测试资产地图                   登记必要测试点与 TEST-ID
        └──────────────┬───────────────────┘
                       ↓
        在 TESTS.md 汇总已有能力和测试缺口
        ↓
开发者编写功能代码和对应测试
        ↓
测试审查（v1 由主会话按 skill 执行）判断测试是否真正证明了规则
        ↓
测试通过后标记为“已覆盖”
        ↓
REGRESSION.md 登记模块改动后应重跑的验收命令
        ↓
regression-auditor 在交付前执行本模块及下游回归
```

这套能力不是为了追求“测试数量更多”，而是让重要规则、测试代码和交付证据能够相互对应。

## 3. 为什么单独新增 TESTS.md

建议让两个台账保持不同职责：

| 文档 | 回答的问题 | 使用时机 |
|---|---|---|
| `TESTS.md` | 应该测试什么？为什么测试？目前有没有覆盖？ | 需求设计、开发、修 Bug、测试审查时 |
| `REGRESSION.md` | 修改某个模块以后，必须重跑哪些测试？ | 代码改动完成、准备交付时 |

不建议把二者合并成一个大表：

- 测试清单关注“规则与缺口”，属于开发前和开发中的测试规划；
- 回归台账关注“影响面与执行命令”，属于开发后的交付验证；
- 合并后容易让清单同时承担规划、覆盖、依赖和执行记录，最终难以维护。

二者通过稳定测试编号关联，例如 `TEST-ORDER-001`，避免重复抄写同一事实。

## 4. TESTS.md 管什么

`TESTS.md` 只登记重要的业务规则、关键边界、安全风险、历史 Bug 和跨模块流程，不罗列项目中的每个测试函数。

测试文件名、测试函数数量等可以从代码扫描得到，不应该全部靠人工抄进文档。人工和 Agent 主要维护代码本身看不出来的内容：

- 为什么需要这个测试；
- 它保护哪条业务规则或系统行为；
- 什么输入能够触发风险；
- 正确结果应该是什么；
- 当前是缺口、开发中，还是已有可执行证据；
- 它来自需求、事故、Bug，还是安全约束。

建议状态只有四种：

- `待补`：已经确认需要测试，但还没有测试代码；
- `开发中`：测试正在编写或修正；
- `已覆盖`：有对应测试文件、有效业务断言和可执行命令，实际运行通过，并已进入标准测试入口或具名专用任务；
- `不适用`：经过明确判断不需要自动化测试，并写明理由。

### 4.1 入口 A：盘点和维护现有测试资产

主会话按 test-collaboration skill 扫描项目现有测试目录、测试配置、包管理脚本和 CI 命令，先回答“项目现在有什么测试”。扫描对象至少包括：

- `tests/`、`test/`、`__tests__/`、`e2e/` 等测试目录；
- `pytest` markers、Vitest/Jest/Playwright 配置及 package scripts；
- CI 中真实执行的测试命令；
- 测试文件、测试节点、fixtures、golden sample 和对账脚本；
- 能安全执行时的测试收集结果，例如 `pytest --collect-only`。

扫描结果不逐函数抄进文档，而是按“模块/测试套件/运行命令”聚合成测试资产地图。每次盘点同时给出四种判断：

- `必要`：保护关键规则、关键链路或高风险边界，应保留；
- `重复`：多条测试可能在重复证明同一行为，待人工确认是否合并；
- `缺失`：关键模块或流程没有对应层级的测试；
- `疑似废弃`：测试指向已下线功能、失效路径或 CI 不再执行的命令，待人工确认，Agent 不得自行删除。

测试资产地图采用事件触发式维护，不设置容易失真的固定天数：

1. 首次采用 TESTS.md 时做一次全量盘点；
2. 测试目录、测试配置、标准运行入口或 CI 任务发生变化时，复核受影响模块；
3. 新增、关闭或改变 TEST-ID，以及新增/关闭 Bug 时，顺带复核对应模块行；
4. 重大功能、接口契约或模块依赖变化时，复核相关测试层级和缺口；
5. 发布、阶段交付或 `/governance-sync` 前，确认本阶段改动涉及的资产地图仍然真实；
6. 只有测试体系重构或地图普遍失真时才重新全量扫描，日常以受影响模块增量维护为主。

### 4.2 测试类型采用“层级 + 用途”双标签

单元、集成和端到端描述测试覆盖的**层级**；回归描述测试存在的**用途**，两者不能混成互斥分类。一条测试可以同时是“端到端测试 + 回归保护”，也可以有多个用途。用途必须从受控词表中选择，不能临时发明新值。

| 维度 | 类型 | 主要回答的问题 |
|---|---|---|
| 层级 | 单元测试 | 单个函数、规则或计算是否正确 |
| 层级 | 集成测试 | 模块、数据库、API 或外部适配器能否正确协作 |
| 层级 | 端到端测试（E2E） | 用户关键业务流程能否从入口走到最终结果 |
| 层级 | 契约测试 | 前后端或服务间字段与行为是否符合唯一契约 |
| 层级 | 冒烟测试 | 系统最基本的启动和核心入口是否可用 |
| 用途 | 规则保护 | 业务公式、字段口径、状态转换等规则是否持续正确 |
| 用途 | 关键链路 | 登录、下单、付款、报表生成等关键用户流程是否可用 |
| 用途 | 回归保护 | 历史正确行为或已修 Bug 是否不会再次出错 |
| 用途 | 专项保护 | 权限、数据泄露、性能、兼容性等专项风险是否受控 |

受控用途值仅为：`规则保护`、`关键链路`、`回归保护`、`专项保护`。需要多个用途时用逗号并列，例如 `关键链路, 回归保护`。

### 4.3 怎么判断某类测试有没有必要

测试必要性不靠“文件数量”判断，而按风险和失败后果判断：

1. 金额、权限、数据加工、外部契约、关键用户流程和历史 Bug，必须有测试；
2. 纯函数和单条计算规则优先单元测试；
3. 模块交接、数据库、文件或网络边界优先集成/契约测试；
4. 登录、下单、付款、报表生成等关键完整流程至少有一条 E2E 或真实路径验收；
5. 同一规则已有更强测试覆盖时，新增重复测试必须说明额外价值；
6. 功能已下线或测试从未进入执行链路时，标记“疑似废弃”并交给人确认，不自动删除。

### 4.4 入口 B：Bug 清单强制转测试点

主会话读取项目 Bug 清单、issue、审计问题清单或事故记录。每个已确认的有效 Bug 都必须回答：“哪一个 TEST-ID 永久防止它复发？”

```text
BUG-035
  ↓ 提取真实故障输入和预期结果
TEST-BUG-035（状态：待补）
  ↓ 修复前先确认测试失败
修复代码
  ↓ 修复后确认测试通过
TEST-BUG-035（状态：已覆盖，用途：回归保护）
```

Bug 关闭的最低证据包括：Bug 来源、复现输入、预期结果、测试层级、测试文件/节点、运行命令，以及修复前失败和修复后通过的事实。无法自动化时也必须在 TESTS.md 登记，并写清人工验收方式和不能自动化的原因。

### 4.5 从 Hermes 借鉴的测试纪律

Hermes 的测试规模和运行器不适合直接复制到所有项目，但以下纪律应进入 test-collaboration：

1. **标准测试入口**：每个项目登记一个默认测试命令，保证本地与 CI 使用相同入口；单条测试通过但未进入默认入口或专用 CI 任务，不得视为稳定覆盖。
2. **默认与专用分组**：快速、无外部依赖的测试默认运行；需要 API Key、Docker、真实平台或较长时间的集成/E2E/性能测试进入具名专用任务，并写明触发条件。
3. **E2E 边界透明**：E2E 必须写清从哪个入口到哪个出口、哪些内部路径真实执行、哪些外部依赖使用 fake/mock。不能把只测单个函数的测试命名为 E2E，也不能因为外部平台被 mock 就否认内部完整链路的 E2E 价值。
4. **Bug 保留真实故障形状**：Bug 回归测试记录原平台/环境、真实故障输入和修复前错误表现。高风险 Bug 优先同时补快速单元保护和真实路径/集成/E2E 保护。
5. **行为契约和不变量优先**：测试“数据之间必须保持的关系”和用户可观察行为，不冻结工具数量、枚举长度、当前模型列表等预期会变化的快照。
6. **fixture/fake 复用**：多个测试共享的平台事件、会话、数据库、文件样本或 API 响应，应沉淀到 `fixtures/`、`fakes/` 或测试框架公共 fixture；fake 只替代外部边缘，不应把需要验证的核心内部路径一起 mock 掉。
7. **正反断言**：高风险测试既检查正确结果存在，也检查禁止结果和副作用没有发生，例如密钥未泄露、未审批前没有提交、库存不足时没有创建订单。

不在 v1 照搬 Hermes 的内容：每文件独立进程、并行分片、耗时缓存、进程树清理和复杂 CI 矩阵。这些属于大型仓库运行基础设施，不是测试治理方法论的起步条件。

```markdown
- 执行分组：默认
- 测试边界：订单服务 → 库存检查 → 创建结果
- 真实部分：订单与库存模块协作
- 模拟部分：外部消息通知
- 测试文件：待补
- 运行命令：待补
```

## 6. 专职测试审查 Agent

> 2026-07-12 拍板：本节 agent 与 §8 命令均为二期设计，v1 不建（见 §11）；v1 的测试审查由主会话按 skill 人肉执行。执行边界铁律：test-auditor 跑命令只为验证"已覆盖"标记属实（审查时机）；regression-auditor 跑命令是交付门禁（交付时机）——同一动作、不同目的、不同时机，互不代劳。

二期建议新增：

- 方法论：`skills/engineering/test-collaboration/SKILL.md`
- Agent：`agents/test-auditor.md`
- 命令：`commands/test-audit.md`
- 模板：`templates/TESTS.example.md`

Agent 的定位不是“替开发者随便多写几个测试”，而是测试证据审查员：

> 审查重要规则是否有对应测试，测试是否真的覆盖了所声称的场景，以及“已覆盖”是否有可执行证据。

### 6.1 test-auditor 应该审查什么

1. **需求对应性**：新增需求、契约变更和 Bug 修复是否在 `TESTS.md` 中有对应测试点。
2. **场景真实性**：测试输入是否真的能触发风险，而不是只测最顺利的正常情况。
3. **预期明确性**：预期结果是否可判断，避免“能运行”“没有报错”这种弱结论。
4. **证据有效性**：标记“已覆盖”的条目是否存在测试文件、测试节点和运行命令。
5. **执行真实性**：登记的命令能否真实执行，退出码是否为 0。
6. **断言强度**：测试是否验证业务结果，而不是只验证函数被调用或 mock 被触发。
7. **边界覆盖**：空值、异常值、权限、安全边界和历史故障输入是否遗漏。
8. **清单漂移**：测试被删除、重命名或失效后，清单是否仍错误地标记为“已覆盖”。

### 6.2 test-auditor 不应该做什么

- 不负责扫描模块下游并决定改动后跑哪些回归测试，这是 `regression-auditor` 的职责；
- 不以测试数量或覆盖率百分比代替业务规则判断；
- 不因为测试文件存在就判定“已覆盖”；
- 审计模式下只报告问题，不直接修改生产代码或放松断言；
- 不把所有测试函数抄进 `TESTS.md`，避免制造第二份容易腐烂的文件索引。

## 7. 两个 Agent 的分工

> 本节是二期角色设计，v1 不创建 `test-auditor`，由主会话按 test-collaboration skill 执行测试盘点和测试审查。

| Agent | 核心问题 | 输入 | 输出 |
|---|---|---|---|
| `test-auditor` | 测试设计和证据够不够？ | `TESTS.md`、需求/契约、测试代码、Bug 记录 | 缺口、弱测试、失效引用、执行结果 |
| `regression-auditor` | 本次改动有没有弄坏自己或下游？ | git diff、`REGRESSION.md`、验收命令 | 本模块及下游的红绿判决 |

简单理解：

- `test-auditor` 判断“题目出得对不对、答案能不能证明规则”；
- `regression-auditor` 判断“这次改完以后，相关试卷有没有全部重新考过”。

## 8. 命令设计建议

> 2026-07-12 拍板：命令属二期，v1 不实现（见 §11）。

二期建议只提供一个命令，避免入口过多：

```text
/test-audit init       首次扫描项目，生成 TESTS.md 草稿
/test-audit            审查当前需求或代码改动涉及的测试清单
/test-audit TEST-ID    审查指定测试点
```

### init 模式

- 扫描现有测试目录、测试配置、CI 和运行脚本，按模块/测试套件形成“测试资产地图”；
- 给现有测试标注层级（单元/集成/E2E/契约/冒烟）和用途（回归/安全/性能等）；
- 判断必要、重复、缺失和疑似废弃，所有删除建议必须等人确认；
- 从项目文档、契约、历史 Bug 中寻找重要规则候选；
- 读取 Bug 清单，为每个已确认且尚无保护的 Bug 建立 TEST-ID；
- 能确定对应关系的条目标记为“待确认”；
- 找不到测试证据的规则标记为“待补”；
- 不允许仅凭测试名称自动宣称业务规则已经覆盖。

### 日常审查模式

- 根据 `git diff`、当前需求或用户指定模块确定审查范围；
- 查找对应 `TESTS.md` 条目；
- 检查测试代码与断言；
- 运行登记命令并记录退出码；
- 输出“已覆盖 / 待补 / 弱覆盖 / 引用失效 / 执行失败”。

## 9. 与开发流程的结合

### 测试维护盘点

1. 主会话扫描测试目录、配置、CI 和可执行的测试收集结果；
2. 按模块/套件汇总现有测试，标注“层级 + 用途”；
3. 对照关键模块、关键业务流程和 Bug 清单，判断必要、重复、缺失和疑似废弃；
4. 将聚合结果更新到 TESTS.md 的测试资产地图，将缺口登记为 TEST-ID；
5. 疑似重复或废弃的测试只形成建议，必须由人确认后才能修改或删除。

### 新功能

1. 需求确认后，在 `TESTS.md` 写明关键验收场景；
2. 状态先标记为“待补”；
3. 开发功能并补测试；
4. 测试审查（v1 由主会话按 skill 执行）检查测试设计和执行证据；
5. 审查通过后更新为“已覆盖”；
6. 将需要交付时重复运行的命令关联进 `REGRESSION.md`。

### Bug 修复

1. 从 Bug 清单读取已确认问题，为其建立唯一 TEST-ID；
2. 用真实故障输入新增一个能稳定复现 Bug 的测试点，并标注“测试层级 + 回归保护用途”；
3. 修复前确认测试失败，证明它确实捕获了问题；
4. 修复代码后确认测试通过；
5. 在 `TESTS.md` 记录 Bug 来源、复现输入和测试证据；
6. 由 `regression-auditor` 执行相关模块及下游回归；没有 TEST-ID 或明确的人工验收理由，Bug 不得宣称闭环。

### 交付前

1. 测试审查（v1 由主会话按 skill 执行）确认重要规则没有“口头覆盖”；
2. `regression-auditor` 运行本次改动涉及的全部回归命令；
3. 两边都没有阻塞项，才可以说明测试闭环完成。

## 10. 为什么这样做

### 10.1 测试代码只能告诉我们“测了什么”，不总能告诉我们“为什么测”

大型项目里经常存在几百甚至几千个测试，但重要业务规则仍可能遗漏。测试清单把规则、风险和测试证据连接起来，让人和 Agent 能判断覆盖是否有意义。

### 10.2 “测试通过”不等于“需求被证明”

测试可能只覆盖正常输入、mock 掉关键依赖，或者断言过弱。测试审查需要检查输入、预期和断言之间是否真的形成证据链；v1 由主会话按 skill 执行，二期再决定是否固化为专职 Agent。

### 10.3 测试缺口需要像开发任务一样被看见

没有清单时，“以后补测试”通常只存在聊天记录或人的记忆里。`TESTS.md` 把它变成可分配、可更新、可审查的项目资产。

### 10.4 规划测试和执行回归是两个不同动作

一个负责决定“应该有什么考试题”，另一个负责决定“这次改动需要重考哪些题”。职责分开后，两个 Agent 的判断边界更清楚，也更容易自动化。

### 10.5 符合 docs-governance 的非重叠原则

每个事实只保留一个主要归属：

- 测试目的、业务场景、覆盖状态与判定点只放在 `TESTS.md`（判定点清单自 module-regression 迁入，唯一归属，见 §3.1）；
- 模块下游关系和改后必跑命令只放在 `REGRESSION.md`，判定点以 TEST-ID 回引；
- 具体断言和执行逻辑只放在测试代码；
- 执行历史不存档：验证靠审计时现场重跑命令取退出码；`PROJECT_LOG.md` 只追加两类一行事件——测试点状态翻转、交付节点回归判决。

文档之间用测试 ID 和路径引用，不复制整段内容。

## 13. 当前建议结论

建议继续推进，但先作为独立能力试用，不立即把它做成重量级测试管理系统。

最小成功标准：

- 一个真实项目能生成现有测试资产地图，并识别至少一个缺失、重复或疑似废弃项；
- 一个真实项目能用 `TESTS.md` 找出至少一个此前未被测试的重要规则；

- 补测试后，测试审查（v1 由主会话按 skill 执行）能用文件、断言和退出码证明该规则已覆盖；

- 团队维护成本低于它减少的遗漏和返工成本。

### 14.3 追加讨论：一个 Agent 挂两个 skill 行不行（小磊提议）

小磊提议：不分 test-auditor / regression-auditor 两个 agent，插件里写**一个测试 Agent**，按需调用 test-collaboration 和 module-regression 两个 skill。

Claude 的判断：**技术可行，但它解决的是次要问题（入口数量），解决不了 14.1 的硬伤**——撞车发生在文档层（两份台账记同一事实），不在 agent 层。就算只有一个 Agent 读写，它面对的还是两份重叠文档，改测试要同步两处，漏一处就漂移。腐烂的是文档，不是 Agent。

单 Agent 方案本身的利弊：

**利**
- 入口和文件数少，符合插件"保持轻量"的自我约束；
- skill 是方法论唯一源，一个 Agent 按需读两份不违反现有架构（docs-governor 已是此模式）。

**弊（两条实的）**
1. **成本档位锁死**：regression-auditor 现为 sonnet——故意的，纯机械活（跑命令抄退出码）、每次改动都跑、要便宜；测试设计审查（断言强度、场景真实性）是判断活，要更强模型。一个 Agent 只能填一个 model，合并后要么机械活用贵模型，要么判断活用便宜模型。
2. **门禁不能有想法**：回归审计是交付门禁，价值在于**无聊、确定、只看退出码**。合并后同一 Agent 带着判断力跑门禁，容易在该报红绿时多嘴"顺便建议加个边界测试"，交付节奏被拖住，"裁判只报不修"的铁律边界也变模糊。

**结论：此问题是末端决策，v1 按 14.2 第 5 条根本不建 agent；试点跑完自然知道测试审查多久干一次、需要多强判断力，届时再拍一个还是两个，是五分钟的决定。现在争这个顺序反了。**
